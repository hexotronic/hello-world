# Phase 2 — Architecture

Target: **Minecraft Java 26.3**, **NeoForge 26.3.0.69-beta**, **Java 25**, ModDevGradle 2.0.148.
Mod ID `thaumicunity`, base package `dev.thaumicunity`.

## 0. Implementation status (end of phase 3)

This document is the phase 2 design. What phase 3 built follows it, with these differences:

* **Client calls from common code** go through `common.item.ClientBridge`, which the client entry point
  (`client.ThaumicUnityClient`) replaces with a real implementation; client-bound packet handlers are registered
  there too. There is no `ClientPayloadHandler` class.
* **API**: `ThaumicUnityApi`, `api.event` (`ScanEvent`, `ResearchCompletedEvent`, cancellable `SpellCastEvent`)
  and `api.spell` (`SpellPrimitive`, `SpellContext`, `SpellTarget`, `SpellDelivery`, `SpellParams`). The aspect,
  research and aura sub-packages and the warp/aura change events come with phase 7.
* **Data maps**: the alchemical furnace reads burn time from `thaumicunity:alchemical_fuel`; the essentia it makes
  comes from item aspects. Aura profiles hold base vis and six primal weights; flux tolerance is the
  `aura.riftPressure` option.
* **Recipes**: `crucible`, `arcane_shaped`, `arcane_shapeless` and `infusion` exist. `infusion_enchantment`,
  `ritual`, `salis_conversion` and the `instability_event` registry are later phases (Salis Mundus conversions are
  in code for now). `compat` and `datagen` are empty; data is generated by `tools/gen_content.py` instead.
* **World generation** goes through the `thaumicunity:add_features` biome modifier type, which honours the
  `world.worldgen` option.
* **Testing**: besides the `core` unit tests, in-game tests (`common.gametest.TUGameTests` with
  `data/thaumicunity/test_instance/`) run on a dedicated server via `./gradlew runGameTestServer`, in CI after every
  build.

## 1. Layering

```
dev.thaumicunity
├── api        Public, documented, stable API (other mods compile against this only)
├── core       Pure Java game logic with no Minecraft imports — unit-tested in plain JUnit
├── common     Minecraft-side implementation (both physical sides)
├── client     Rendering, screens, particles, input (loaded only on the client dist)
├── compat     Optional integrations, one sub-package per mod, loaded only when that mod is present
└── datagen    Data generators (run with ./gradlew runData)
```

Rules:
1. `core` never imports `net.minecraft.*` or `net.neoforged.*`. It holds the rules of the game: aspect algebra,
   spell compilation and balancing, research graph validation and mode conversion, aura simulation maths,
   infusion stability, insight puzzle solving, aspect inheritance. Unit tests cover it (`src/test/java`).
2. `common` adapts `core` to Minecraft: registries, codecs, block entities, menus, networking, events.
3. `client` code is reached only through `@Mod(dist = Dist.CLIENT)` entry points and client-bus subscribers.
   Common code never references client classes; packets that need client handling dispatch through
   `ClientPayloadHandler`, which is only class-loaded on the client.
4. `api` contains interfaces, records, registry keys and events. Implementations live in `common`.

## 3. Registries

### 3.1 Static registries (Java, `DeferredRegister`)
Blocks, items, block entity types, menus, recipe types, recipe serializers, recipe book categories, data
component types, attachment types, particle types, sound events, entity types, creative tabs, mob effects,
and the **spell primitive** registry (`thaumicunity:spell_primitive`, a NeoForge custom registry created in
`NewRegistryEvent`) that maps a primitive ID to Java code.

### 3.2 Datapack registries (JSON, `NewDatapackRegistryEvent`)
World registries with a network codec, so clients receive them on login:

| Registry key | Path in a datapack | Value |
|---|---|---|
| `thaumicunity:aspect` | `data/<ns>/thaumicunity/aspect/<id>.json` | colour, components, glyph, flags |
| `thaumicunity:research_category` | `data/<ns>/thaumicunity/research_category/<id>.json` | icon, background, order, required research |
| `thaumicunity:research` | `data/<ns>/thaumicunity/research/<id>.json` | category, position, parents, stages, rewards, flags |
| `thaumicunity:spell_component` | `data/<ns>/thaumicunity/spell_component/<id>.json` | kind, primitive, params, aspect, costs, visuals |
| `thaumicunity:spell_synergy` | `data/<ns>/thaumicunity/spell_synergy/<id>.json` | required aspects/effects, result |
| `thaumicunity:golem_part` | `data/<ns>/thaumicunity/golem_part/<id>.json` | slot, stats, behaviours |
| `thaumicunity:wand_rod`, `thaumicunity:wand_cap` | … | capacity, discount, recipe hints |
| `thaumicunity:warp_event` | … | weight, minimum warp, action |
| `thaumicunity:instability_event` | … | weight, severity, action |

### 3.3 Data maps (`RegisterDataMapTypesEvent`, synced, reloadable)
| Data map | Registry | Value |
|---|---|---|
| `thaumicunity:aspects` | item | `AspectList` (explicit aspect values) |
| `thaumicunity:entity_aspects` | entity_type | `AspectList` (scanning mobs) |
| `thaumicunity:aura_profile` | worldgen/biome | base vis, flux tolerance, six primal weights |
| `thaumicunity:infusion_stabilizer` | block | stability contribution |
| `thaumicunity:essentia_fuel` | item | essentia yield in the alchemical furnace (defaults to item aspects) |

### 3.4 Recipes (`RecipeType` + `RecipeSerializer` record)
`thaumicunity:crucible`, `thaumicunity:arcane_shaped`, `thaumicunity:arcane_shapeless`, `thaumicunity:infusion`,
`thaumicunity:infusion_enchantment`, `thaumicunity:ritual` (multi-stage), `thaumicunity:salis_conversion`
(world-interaction recipes like TC's *Salis Mundus* on a bookshelf). Each declares its research requirement
(`"research": "thaumicunity:alchemy/basic_crucible"`) and is hidden from viewers until known (configurable).

## 5. Player state and world state

| State | Storage | Sync |
|---|---|---|
| Research progress, scans, knowledge points, aspect pool, known spells | `PlayerKnowledge` attachment on the player (`copyOnDeath`) | Full sync on login/respawn/dimension change, delta payloads on change |
| Warp (permanent, sticky, temporary) | `Warp` attachment on the player | Attachment sync |
| Trinket inventory | `Trinkets` attachment | Menu |
| Chunk aura (vis, flux, base, attunement) | `ChunkAura` attachment on `LevelChunk` (serialised with the chunk) | Sent for the chunk the player stands in when it changes by more than a threshold, and when the player holds a scanning item |
| Aura nodes | Block entities | Block entity update packets |
| Device inventories/essentia | Block entities via NeoForge transfer API (`ResourceHandler`) | Menus/update tags |

## 6. Performance budget

* Aura: at most `aura.chunks_per_tick` (default 64) chunks per level per tick are simulated, in round-robin
  over loaded chunks; each update is O(1) plus four neighbour reads. Unloaded chunks catch up lazily on load
  using elapsed game time (closed-form regeneration from `AuraSimulator.catchUp`).
* Taint spread: bounded by `taint.max_spread_per_tick`; positions are queued, never scanned.
* Aspect resolution: done once per data reload, off the main thread where NeoForge allows, memoised.
* Particles: every effect has a `particle_density` multiplier; client config `visuals.particle_quality`
  (`minimal`, `decreased`, `all`) scales them; shader effects can be turned off individually.

## 7. Networking

All payloads are records implementing `CustomPacketPayload` with `StreamCodec`s, registered in
`RegisterPayloadHandlersEvent` with protocol version `"1"`. Server → client: aspect table, knowledge sync and
deltas, aura snapshot, spell effect visuals (seeded so clients reproduce particles without per-particle
packets). Client → server: research table actions (place aspect, solve, draw card), focus workbench edits,
caster key actions (change focus). Every client → server handler validates the player's menu/reach/known
research before acting.

## 8. Public API surface

`dev.thaumicunity.api.ThaumicUnityApi` is the single entry point:
* `aspectsOf(ItemStack)`, `aspectsOf(EntityType)`, `aspect(Identifier)`;
* `knowledge(Player)` → `ResearchQuery` (`isComplete`, `stageOf`, `hasScanned`);
* `aura(Level)` → `AuraAccess` (`vis`, `flux`, `drainVis`, `addFlux`);
* registry keys for every datapack registry;
* `SpellPrimitive` interface plus `TURegistries.SPELL_PRIMITIVE` for adding Java-backed spell effects;
* events on `NeoForge.EVENT_BUS`.
Other mods add aspects, research, recipes, spell components, golem parts and warp events with **plain JSON**;
Java is only needed for brand-new behaviour (new primitives, devices).

## 9. Compatibility rules

* Tags: all ores/ingots/nuggets/gems/storage blocks/raw materials use `c:` tags
  (`c:ingots/thaumium`, `c:storage_blocks/thaumium`, `c:ores/cinnabar`, `c:gems/amber`, …) and our own
  tags for behaviour (`thaumicunity:infusion_stabilizers`, `thaumicunity:taint_immune`,
  `thaumicunity:crucible_heat_sources`).
* No mixins, no access transformers (DESIGN_DECISIONS D15). Vanilla behaviour is never changed globally;
  everything hooks events and checks our own state first.
* Every integration lives in `compat/<modid>` and is loaded only through `ModList.get().isLoaded(modid)` checks
  or the integration's own plugin discovery (JEI `@JeiPlugin`, EMI entrypoints, …), so a missing mod can never
  cause a class-loading error.
* Every major feature is behind a config switch (see `TUConfig`).
